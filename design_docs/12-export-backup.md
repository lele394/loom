# 12 — Export, backup and restore

Data ownership is a v1 requirement, not a later feature. There are two distinct formats with different jobs:

| | Portable export | Backup |
| --- | --- | --- |
| Purpose | Read your data without Loom; move/archive | Exact restore of the instance |
| Format | JSONL + Markdown + BibTeX + originals + manifest | SQLite snapshot + originals + manifest |
| Includes credentials | No (no password hashes, no API keys, no sessions) | Yes, encrypted fields as stored |
| Restorable in-app | Not in v1 (manual/scripted) | Yes |
| Size | Similar | Slightly smaller (no Markdown duplication) |

---

## 1. Export

### 1.1 Single objects

- `GET /export/notes/:id.md` — Markdown with YAML front matter:

```markdown
---
id: note_01JB…
title: Frequency scaling observations
project: HPC Energy Efficiency
template: research
tags: [dvfs, measurements]
created: 2026-11-16T08:12:00.000Z
updated: 2026-11-16T15:10:00.000Z
---

## Observations
…
```

- `GET /export/references.bib` — BibTeX for all references or `?ids=…`.
- `GET /api/v1/attachments/:id/download` — original file.

### 1.3 Workspace archive

Same layout with `projects/` grouped per project and global objects at the root, plus:

```
├── data/
│   ├── users.jsonl            (no password hashes)
│   ├── conversations.jsonl
│   ├── messages.jsonl
│   ├── daily_digests.jsonl
│   ├── digest_revisions.jsonl
│   └── settings.json          (AI keys redacted)
```

### 1.4 Manifest (export)

```json
{
  "format": "loom-export",
  "formatVersion": 1,
  "appVersion": "0.1.0",
  "schemaVersion": 1,
  "createdAt": "2026-11-16T18:00:00.000Z",
  "scope": { "kind": "workspace" } ,
  "counts": { "objects": 412, "notes": 87, "attachments": 63 },
  "files": [{ "path": "data/notes.jsonl", "sha256": "…", "size": 12345 }]
}
```

### 1.5 Rules

- Exports are generated by a read-only transaction/snapshot so counts and rows are consistent.
- JSONL: one JSON object per line, no pretty printing, UTF-8, LF. Field names match the database columns to make joins obvious. Web archives are ordinary attachments and are exported/backed up with the rest of the files.
- Filenames are sanitised ASCII slugs; IDs disambiguate collisions.
- Attachments are named `<hash>__<safe-original-name>` and mapped in `attachments.jsonl`.
- Checksums cover every file except `checksums.sha256`.
- Streaming zip; no temp copy of attachments.

## 2. Backup

### 2.1 Archive format

```
loom-backup-2026-11-16T030000Z-<kind>/
├── manifest.json
├── README.txt
├── db/loom.db
├── attachments/<aa>/<bb>/<sha256>
└── checksums.sha256
```

Manifest:

```json
{
  "format": "loom-backup",
  "formatVersion": 1,
  "appVersion": "0.1.0",
  "schemaVersion": 7,
  "createdAt": "…",
  "kind": "manual",
  "counts": { "objects": 412, "attachments": 63, "events": 12043 },
  "keyFingerprint": "a1b2c3d4",
  "files": [{ "path": "db/loom.db", "sha256": "…", "size": 12345678 }]
}
```

`keyFingerprint` is the first 8 hex chars of SHA-256 of the master key, used to warn that encrypted AI keys will not decrypt if the key changes.

### 2.2 Creation algorithm

1. Create a row (`status=ready` only on success) with a temp filename.
2. `db.backup()` → `data/tmp/<id>.db` (online, transactionally consistent).
3. Open the copy read-only: `PRAGMA integrity_check` must return `ok`.
4. Collect referenced blobs and add them unchanged.
5. Write manifest, README, checksums; stream ZIP to `backups/<name>.zip.partial`; fsync; rename.
6. Update the row (size, checksum of the zip, filename); emit `backup.created`.
7. Enqueue pruning.

Backups never run inside a request transaction and never block writes (SQLite's online backup API handles pages safely). Zip creation is CPU-bound; v1 accepts this (single user), with a note to move it to a worker thread if it becomes noticeable.

### 2.3 Retention

| Kind | Default retention |
| --- | --- |
| auto | last 14 |
| manual | keep until deleted |
| pre_migration | last 3 |
| pre_restore | last 3 |

Pruning deletes files and rows. The newest successful backup is never deleted. Retention is configurable (1–365) in Settings.

### 2.4 Verification

`POST /backups/:id/verify`:
- Recompute the ZIP checksum and compare with the stored one.
- Extract the manifest, verify every listed file hash.
- Open the inner DB, run `integrity_check` and a few sanity queries (`users` non-empty, counts match manifest).
- Report `{ok, errors[], checkedFiles, tookMs}`; a failed verification marks the backup `failed` but does not delete it.

## 3. Restore

### 3.1 Preconditions

- Admin session, CSRF token, `confirm=RESTORE` form field.
- Server enters a maintenance flag: write endpoints return `503 restore_in_progress` for the duration. Reads may continue until the import transaction starts.
- A `pre_restore` backup of the current state is created first; if it fails, the restore aborts.

### 3.2 Algorithm

1. Stream the upload to `data/tmp/restore-<id>/archive.zip` (max 10 GB, cap configurable).
2. Validate ZIP entries: no absolute paths, no `..`, no symlinks, max 200k entries, max uncompressed size check.
3. Extract to a temp directory.
4. Parse and validate manifest: format, `formatVersion` supported (1), `schemaVersion` ≤ current schema, kind, files list.
5. Verify SHA-256 for every listed file and every `attachments/**` entry.
6. Open `db/loom.db` read-only: `integrity_check`, required tables present, `schema_migrations` max version equals manifest schema version.
7. Check that every `blob_hash` referenced in the backup DB exists in the extracted attachments; otherwise abort with a precise error.
8. Copy all blobs into the live store (content-addressed, atomic; existing files skipped). This is safe even if the import later fails.
9. Start the import transaction:
   - `PRAGMA foreign_keys=OFF` (set outside the transaction).
   - `BEGIN IMMEDIATE`.
   - Delete all rows from data tables in reverse dependency order. The current session row is preserved until the end, and the running backup row is not touched.
   - Import rows table by table in dependency order, transforming nothing (same schema). **Skip** `sessions`, `jobs`, `search_fts` and `chunks_fts` (no stale sessions/jobs; the search indexes are rebuilt deterministically after restore).
   - `PRAGMA foreign_key_check` must return no rows.
   - Commit; on any error, roll back (the old data is intact).
10. Restore `settings` (the master key itself is not stored in backups). AI provider ciphertexts are restored but may be undecryptable if `keyFingerprint` differs — the response warns and the UI asks for keys again.
11. Delete **all** sessions (including the current one) and return `reloginRequired: true`; the client redirects to login. This prevents restored-but-stale session material from being usable.
12. Enqueue `search.reindex` and `embed.chunks`; emit `backup.restored`.
13. Clean the temp directory; clear the maintenance flag.

### 3.3 Guarantees

- **Atomicity:** the data swap is one transaction; a failure leaves the previous database untouched.
- **Validation before mutation:** checksums, integrity and schema are verified before the transaction.
- **Safety net:** pre-restore backup, downloadable.
- **Partial restore** (single project/note) is not supported in v1. Workaround: restore the full backup into a scratch instance, export the desired objects, and copy them as Markdown/BibTeX. Documented; object-level import is P2.

### 3.4 Compatibility

- Backups are versioned. A newer `formatVersion` than the app supports is rejected with an upgrade hint.
- Older schema backups are accepted only when the app can migrate them; since the import is row-based, only the **current** schema version is supported in v1. A backup from an older app version must be restored with that version first, then upgraded. (This is a deliberate simplicity trade-off; schemaVersion 1 is the first release.)
- `LOOM_SECRET`/`master.key` must be preserved to decrypt AI keys; everything else restores without it.

## 4. Scheduling and offsite

- Daily automatic backup (default 03:00 local) and before each migration or restore.
- `LOOM_BACKUP_DIR` may point to another mounted disk; the directory must be writable.
- Optional post-backup copy to S3/NAS is P2. Until then, the README documents a `rsync`/restic recipe, which is more robust than a bespoke implementation for v1.
- Backups are not encrypted by Loom; use filesystem/restic encryption for offsite copies. Documented in Settings and README.

## 5. What is not exported, and why

| Data | Portable export | Backup | Reason |
| --- | --- | --- | --- |
| Password hash | ✗ | ✓ | Credentials are not user data; backup must be restorable |
| AI API keys | ✗ | ✓ (encrypted) | Never expose secrets in a shareable archive |
| Sessions | ✗ | ✗ | Ephemeral and security-sensitive |
| Jobs | ✗ | ✗ | Recreated from current state |
| FTS index | ✗ | ✓ (in DB file) | Rebuildable; excluded from portable export to avoid stale duplicates |
| Chunks with embeddings | ✗ | ✓ | Rebuildable but expensive; included in the DB snapshot |

## 6. Verification tests

- Export → unzip → parse every JSONL line → note Markdown front matter matches object.
- Backup → verify → restore into a fresh data directory (test harness) → row counts and a sample note/PDF hash match.
- Restore of a tampered archive fails before mutation (checksum mismatch).
- Restore of an archive with a missing blob fails before mutation.
- Restore failure mid-import rolls back and the app remains usable.
- Retention removes the oldest auto backup and never the newest.
- Key fingerprint mismatch produces a warning, not a failure.
